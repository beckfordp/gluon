# 0028. Spike a wire-compatible Rust port of user-service

## Status
Proposed (2026-11-08)

## Context
The eight backend services are Scala (cats-effect, purerest, purekafka). Other
services only see them through open contracts:
- REST: paths, status codes, JSON bodies and error shapes, documented as
  OpenAPI generated by purerest.
- Kafka: one topic per domain with a shared envelope ([ADR 0009](./0009-one-kafka-topic-per-domain.md)),
  JSON Schema registered in Apicurio ([ADR 0003](./0003-kafka-schema-registry.md)).
- Outbox plus Debezium ([ADR 0008](./0008-outbox-pattern-via-debezium-cdc.md)):
  the `outbox_events` table layout is the connector's contract. `payload` is
  passed through byte-for-byte by `StringConverter`.
- Postgres schema owned by Flyway SQL migrations.
- Observability: W3C `traceparent` on HTTP and through the outbox, OTLP
  export to Tempo ([ADR 0021](./0021-tempo-trace-backend.md)), Prometheus
  metric names and labels used by the generated dashboards
  ([ADR 0027](./0027-dashboard-architecture.md)), and the log format that
  Filebeat parses.

So any service could in principle be replaced by an implementation in another
language that keeps these contracts. Rust has mature libraries for every one
(axum, sqlx, rdkafka, opentelemetry-otlp, prometheus). Within the solo budget
([ADR 0015](./0015-platform-goal-production-realism-within-a-solo-budget.md)),
a polyglot service is a credible demo of contract-first design, and the port
gives a fair performance comparison with the Gatling harness
([ADR 0019](./0019-gatling-performance-harness.md)).

The unknown is cost. The services themselves are small. Most of the work is
purerest's cross-cutting behaviour (tracing, metrics, resilience, docs, the
log format), which every non-Scala service would have to rebuild. Before
committing to anything larger, a time-boxed spike should measure that.

## Decision
1. **Spike one service: user-service.** Its surface is small: `POST
   /auth/signup`, `POST /auth/login`, `GET /users/{id}`, one Postgres table,
   and it publishes `user-events: UserRegistered` through the outbox. It
   consumes nothing. That still covers REST, Postgres, outbox/Debezium, schema
   registration and tracing end to end. gshop sign-up/login and
   notification-service depend on it, so the existing suites exercise it.
2. **Drop-in replacement, not a rewrite.** Same image port, k8s Service name,
   env/config keys, health endpoints and contracts. Contracts are frozen for
   the spike: if a gap is found, the Rust side changes, not the contract.
3. **Reuse, don't re-derive:**
   - Run the existing Flyway migrations (Flyway container or init Job). Don't
     port them to a Rust migration tool.
   - Use the registered `user-events` JSON Schemas from Apicurio. The Rust
     service checks against them rather than generating its own.
   - Use the same PBKDF2 parameters (`PBKDF2WithHmacSHA256`, 210000
     iterations, same salt/encoding) and token hashing, so users created by
     either implementation can log in to the other.
4. **Separate repo** `services/user-service-rs` with its own conductor setup,
   CI and `GH_PACKAGES_TOKEN`. The Scala service stays the default. The
   deployed implementation is chosen by a kustomize overlay.
5. **Shared-library seam.** Write cross-cutting concerns as a small internal
   crate inside the spike repo (tracing middleware, metrics, log format,
   error envelope), shaped as the seed of a Rust purerest equivalent. Only
   extract it into `lib/` if the follow-up decision is to go further.
6. **Time box: about 5 working days.** Stop when it ends, whatever state
   the work is in, and record the findings.

### Success criteria (all black-box)
- Acceptance (Playwright BDD) and E2E journeys pass, unchanged, with the Rust
  service deployed.
- The OpenAPI diff against the Scala service's spec shows no breaking change.
- `UserRegistered` validates against the Apicurio schema and is consumed by
  notification-service.
- One sign-up → notification trace in Tempo spans both implementations
  without breaks.
- The Service dashboard renders the Rust service with no panel changes.
- Gatling run recorded beside the Scala baseline: latency, throughput, memory,
  image size, startup time.

## Consequences
- The spike outcome will feed a follow-up ADR: stop, keep as a showcase
  service, or plan further ports (leaf services first; order and payment
  last because of their state machines and outbox flows).
- Any contract gap found (e.g. an undocumented error shape or header) gets
  fixed in the documentation or spec, which improves the contracts whatever
  the port decision.
- Short-term cost: a second toolchain (cargo, clippy, rustfmt, cargo-audit or
  Dependency-Track SBOM per [ADR 0013](./0013-dependency-security-scanning-dependency-track.md)),
  plus a second CI pipeline shape.
- pure-service-generator stays Scala-only. A Rust template is deferred until
  the follow-up ADR decides.
- Risk: purerest behaviour that is implicit (retry/circuit-breaker defaults,
  metric label sets, log fields) may only show up as dashboard or trace
  differences, not as test failures. The success criteria check these
  explicitly for that reason.

## Alternatives considered
- **Common Lisp.** Kafka needs FFI to librdkafka and OTLP export would be
  hand-written. Too much infrastructure work for a spike.
- **Clojure.** Reuses the JVM Kafka and OTel libraries, so it shows little
  that the Scala stack doesn't already.
- **Port order-service first.** Highest value, but its saga and outbox
  complexity would mix up the language cost with domain cost.
