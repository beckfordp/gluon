# gluon

The Gluon platform repo — cross-cutting docs, tooling, and infra config.
The six services themselves are each their **own** independent git repo,
generated by hand one at a time via `pure-service-generator` and co-located
under `services/` for convenience only (see "Layout" below) — nothing in
this repo is generated automatically by an agent.

See [`docs/`](./docs/) for the cross-repo vision, user stories, system
design, and ADRs this is built from (moved in from the old iCloud folder —
it wasn't earning its keep on its own, and one folder is easier to keep in
sync with MWeb than two).

**Start with [`PLAN.md`](./PLAN.md)** — the phased, cross-repo order of work
(walking skeleton), what to stub in each repo's own tests, and when to run
`/conductor:setup`. This README is the per-command reference; `PLAN.md` is
the sequencing.

## Layout

```
gluon/
├── docs/            cross-repo vision, user stories, system design, ADRs
├── bin/             platform tooling entry points (generate-service, codegen)
├── services/        each generated service — its own git repo, gitignored here
├── infra/
│   ├── docker/        shared local runtime infra (Kafka, schema registry — not per-service Postgres)
│   ├── k8s/            Helm chart(s), parameterized per environment
│   └── terraform/       EKS/VPC/ECR provisioning (empty until there's an ADR for it)
├── environments/    local/dev/staging/prod config — no secrets committed
├── specs/           codegen field-specs
├── backlogs/        sliced, numbered (US-N.M) per-repo backlog
└── prototype/       the React UI prototype
```

## Per-service run order

1. `bin/generate-service <domain-name> [--field-spec specs/<name>.yaml]`
   — generates `services/<domain-name>-service/`, applies the field-spec (if
   given) via `tools/codegen` (or run `bin/codegen` separately), then runs
   `sbt scalafmt test`. Needs Docker running (Postgres-backed tests) and
   `GITHUB_TOKEN`/`GITHUB_ACTOR` set (see `pure-service-generator`'s own
   README — needed to resolve `purerestlib` from GitHub Packages).
2. Inside the new service directory, in Claude Code: run `/conductor:setup`.
3. Paste `backlogs/<name>.md`'s items into the `## Backlog` section of the
   resulting `conductor/tracks.md`.
4. When ready to push: `gh repo create beckfordp/<name> --public
   --source=. --remote=origin --push` (plain personal-account repo — no
   dedicated GitHub org). This initializes the service's own independent git
   repo right there under `services/`; gluon's own repo has `services/*`
   gitignored, so there's no nested-repo conflict.

## Field specs

`specs/order.yaml`, `specs/inventory.yaml`, `specs/payment.yaml`,
`specs/catalog.yaml`. No spec for `notification-service` (no DB) or
`cart-service` (Redis-primary — doesn't fit the codegen tool's Postgres/flat-
field model; generate the bare scaffold and rework it, see its backlog).

**Enum-like fields:** `tools/codegen` v1 only supports `String`/`Int`/
`Boolean`/`Instant` — no enum type. Convention: spec it as `String`, then add
a backlog item (in that repo's own backlog file) to harden it into a real
Scala enum + Postgres check/enum type post-generation, with the actual value
set spelled out. Currently applies to `order.status` ({pending, reserved,
reservation_failed}) and `payment.status` ({pending, settled, failed}) — see
`backlogs/order-service.md` and `backlogs/payment-service.md`.

**Nested/collection fields:** also not codegen-able (flat scalars only) — a
`lineItems: List[...]`-shaped field can't be spec'd at all. Convention: leave
it out of the field-spec, add a backlog item to hand-write a child table via
its own Flyway migration (`V2__create_<name>.sql`, following the generated
`V1__create_<domain>_table.sql` naming), outside codegen entirely.
- Primary key: `UUID`, **app-generated** (`Sync[F].delay(UUID.randomUUID())`)
  — matches the base entity's own convention; there's no DB-side
  `gen_random_uuid()` default in the generated schema, don't introduce one
  just for a hand-added table.
- FK to the owning entity (same database): a real Postgres `REFERENCES`,
  `ON DELETE CASCADE` if the child rows are owned by and should die with the
  parent (line items with their order, say).
- Reference to another *service's* entity (different database — one-db-per-
  service, ADR-level decision): never a real FK. Snapshot the fields you'll
  need later (name, price at time of reference) as plain columns instead of
  joining live later — otherwise historical records silently show today's
  values. Applied to `order_items` — see `backlogs/order-service.md`.

**FK-shaped fields inside a codegen'd entity:** codegen has no `UUID` type —
`String` always maps to Postgres `TEXT` (checked `FieldRenderers.scala`), so
a field like `payment.orderId` was never going to be a real UUID column or a
real FK (cross-service anyway — no constraint possible regardless of type).
Convention: spec it as `String`, but give it a **UUID-shaped example**
(`"3fa85f64-5717-4562-b3fc-2c963f66afa6"`, not a human-readable placeholder
like `"order-abc"`) since the real values will be actual UUIDs — keeps
generated tests/docs representative of the real shape. This is different
from a hand-written child table's own FK column (like `order_items.order_id`
above), which sits outside codegen entirely and should stay a real `UUID`
with a real constraint when it references a row in the *same* database.
