# gluon

The Gluon platform repo — cross-cutting docs, tooling, and infra config.
The six services themselves are each their **own** independent git repo,
generated by hand one at a time via `pure-service-generator` and co-located
under `services/` for convenience only (see "Layout" below) — nothing in
this repo is generated automatically by an agent.

See [`docs/`](./docs/) for the cross-repo vision, user stories, system
design, and ADRs this is built from.

**Start with [`PLAN.md`](./PLAN.md)** — the index of the cross-repo plans in
[`plans/`](./plans) (order of work, what to stub in each repo's own tests, and when to run
`/conductor:setup`). This README is the per-command reference; `PLAN.md` is
the sequencing. [`TECHNICAL_DEBT.md`](./TECHNICAL_DEBT.md) tracks the
separate list of cross-cutting gaps found while building (not derived from
a user story) that affect more than one repo — CORS, Kafka consumer
resilience, etc.

## Layout

```
gluon/
├── docs/            cross-repo vision, user stories, system design, ADRs
├── bin/             platform tooling entry points (generate-service, codegen, gkube)
├── services/        each generated service — its own git repo, gitignored here
├── frontends/       each frontend app — its own git repo, gitignored here
├── apps/            applications built on the platform (gfood) — own git repos, gitignored here (ADR 0031)
├── tools/           platform tooling repos (pure-service-generator) — own git repo, gitignored here
├── lib/             shared platform library repos (purerest) — own git repo, gitignored here
├── tests/           acceptance (Playwright) and performance (Gatling) suites — own git repos, gitignored here; run via bin/run-acceptance, bin/run-perf
├── infra/
│   ├── docker/        shared local runtime infra (Kafka, schema registry — not per-service Postgres)
│   ├── k8s/            Helm chart(s), parameterized per environment
│   └── terraform/       EKS/VPC/ECR provisioning (empty until there's an ADR for it)
├── environments/    local/dev/staging/prod config — no secrets committed
└── specs/           codegen field-specs
```

## Services

## Running gluon-local in the sandbox: `gkube`

**Sandbox only.** Every other environment runs the real thing: on the laptop gluon-local
is OrbStack's Kubernetes, deployed by `bin/k8s-local-up` (ADR 0002), and the
environments beyond it are real clusters too. The sandbox, where the Rust ports are
developed, has no Docker and no Kubernetes, so there gluon-local runs in **gluon-kube**,
a simulator that reads the same manifests, chart and values files and runs each
workload as a local process in unprivileged namespaces
([ADR 0030](./docs/adr/0030-gluon-kube-sandbox-kubernetes-runtime.md),
[`tools/gluon-kube/`](./tools/gluon-kube), findings in
[`docs/gluon-kube-findings.md`](./docs/gluon-kube-findings.md)). It runs what can run in
the sandbox: the shared infra and the services that can be built there (the Rust
ports); the Scala services can't be built there, so their pods show
`ImageUnavailable`. The laptop pass on OrbStack stays the authority for the cluster.

`bin/gkube` runs it (`gkube` on the PATH after `bin/sandbox-setup`; it works from the
root desktop terminal too).

Start the cluster and deploy user-service-rs with the shared infra (Postgres per
service, Kafka, Kafka Connect with Debezium), as `bin/k8s-local-up` does on the laptop:

```
gkube cluster start
gkube up user-service        # ~3 min (~6 min after bin/sandbox-save removed the Rust build)
gkube get pods               # what has a recipe Running; Redis and Apicurio ImageUnavailable
```

Reach the services by their cluster names from the sandbox (an HTTP proxy on
127.0.0.1:3128), and open the docs in the browser: the REST API (Swagger UI) and the
Kafka events (AsyncAPI):

```
gkube proxy &
taiga-browser --proxy-server=http://127.0.0.1:3128 --new-window \
  http://user-service:8080/docs/ http://user-service:8080/docs/asyncapi/
```

From a terminal:

```
export http_proxy=http://127.0.0.1:3128
curl -i http://user-service:8080/health          # liveness: 200 while the process is up
curl -i http://user-service:8080/health/ready    # readiness: 200 when Postgres answers, else 503
curl -s -X POST http://user-service:8080/auth/signup -H 'Content-Type: application/json' \
  -d '{"email": "me@example.com", "password": "correct-horse-battery-1"}'
gkube exec deploy/kafka -- /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic user-events --from-beginning --timeout-ms 10000
```

Stop: `kill %1` (the proxy), then `gkube cluster stop`. Every command, the connector
restart if a sign-up doesn't reach `user-events`, and how names work inside and outside
the cluster: [`tools/gluon-kube/README.md`](./tools/gluon-kube/README.md). To review what
is built: `bin/verify-complete-kube-spike.sh` (every feature exercised, ~15 min, no side
effects).

## Demo data (local only)

`bin/seed-demo-data` creates three demo customers (`ada.demo@example.com`,
`grace.demo@example.com`, `alan.demo@example.com`, password
`demo-password-1`) and six orders across the live states (authorized with
PENDING/PICKING fulfilment, confirmed, cancelled, payment_failed,
dispatch_failed). It uses only public APIs, keeps a local state manifest for
idempotent reruns, and supports `--reset`.

Prerequisite: `services/catalog-service/scripts/seed-watches.sh` (seeds the
catalog and inventory stock). **Demo only — never run against a shared or
production environment.**

## Per-service run order

1. `bin/generate-service <domain-name> [--field-spec specs/<name>.yaml]`
   — generates `services/<domain-name>-service/`, applies the field-spec (if
   given) via `tools/codegen` (or run `bin/codegen` separately), then runs
   `sbt scalafmt test`. Needs Docker running (Postgres-backed tests) and
   `GITHUB_TOKEN`/`GITHUB_ACTOR` set (see `pure-service-generator`'s own
   README — needed to resolve `purerestlib` from GitHub Packages).
2. Inside the new service directory, in Claude Code: run `/conductor:setup`.
3. Seed the `## Backlog` section of the resulting `conductor/tracks.md`
   with this service's title-only `US-N.M`/`TD-N.M` items from
   `docs/user-stories.md`/`TECHNICAL_DEBT.md` (see `PLAN.md`).
4. When ready to push: `gh repo create beckfordp/<name> --public
   --source=. --remote=origin --push` (plain personal-account repo — no
   dedicated GitHub org). This initializes the service's own independent git
   repo right there under `services/`; gluon's own repo has `services/*`
   gitignored, so there's no nested-repo conflict.

## Field specs

`specs/order.yaml`, `specs/inventory.yaml`, `specs/payment.yaml`,
`specs/catalog.yaml`. No spec for `notification-service` (no DB) or
`cart-service` (Redis-primary — doesn't fit the codegen tool's Postgres/flat-
field model; generate the bare scaffold and rework it, see its backlog).

**Enum-like fields:** `tools/codegen` v1 only supports `String`/`Int`/
`Boolean`/`Instant` — no enum type. Convention: spec it as `String`, then add
a backlog item (in that repo's own backlog file) to harden it into a real
Scala enum + Postgres check/enum type post-generation, with the actual value
set spelled out. Applied to `order.status` (`{authorized, confirmed,
payment_failed, cancelled, dispatched, dispatch_failed}`, `order-service`'s
`OrderStatus`) and `payment.status` (`{pending, authorized, captured, failed,
voided}`, `payment-service`'s `PaymentStatus`) — both done.

**Nested/collection fields:** also not codegen-able (flat scalars only) — a
`lineItems: List[...]`-shaped field can't be spec'd at all. Convention: leave
it out of the field-spec, add a backlog item to hand-write a child table via
its own Flyway migration (`V2__create_<name>.sql`, following the generated
`V1__create_<domain>_table.sql` naming), outside codegen entirely.
- Primary key: `UUID`, **app-generated** (`Sync[F].delay(UUID.randomUUID())`)
  — matches the base entity's own convention; there's no DB-side
  `gen_random_uuid()` default in the generated schema, don't introduce one
  just for a hand-added table.
- FK to the owning entity (same database): a real Postgres `REFERENCES`,
  `ON DELETE CASCADE` if the child rows are owned by and should die with the
  parent (line items with their order, say).
- Reference to another *service's* entity (different database — one-db-per-
  service, ADR-level decision): never a real FK. Snapshot the fields you'll
  need later (name, price at time of reference) as plain columns instead of
  joining live later — otherwise historical records silently show today's
  values. Applied to `order_items` (sku/product name/unit price snapshotted
  from catalog-service at order time) — done.

**FK-shaped fields inside a codegen'd entity:** codegen has no `UUID` type —
`String` always maps to Postgres `TEXT` (checked `FieldRenderers.scala`), so
a field like `payment.orderId` was never going to be a real UUID column or a
real FK (cross-service anyway — no constraint possible regardless of type).
Convention: spec it as `String`, but give it a **UUID-shaped example**
(`"3fa85f64-5717-4562-b3fc-2c963f66afa6"`, not a human-readable placeholder
like `"order-abc"`) since the real values will be actual UUIDs — keeps
generated tests/docs representative of the real shape. This is different
from a hand-written child table's own FK column (like `order_items.order_id`
above), which sits outside codegen entirely and should stay a real `UUID`
with a real constraint when it references a row in the *same* database.

## Per-frontend run order

1. `npm create vite@latest <name> -- --template react-ts` inside
   `frontends/` — generates `frontends/<name>/`.
2. `git init` inside the new directory (each frontend app is its own
   independent repo, same as a service — `frontends/*` is gitignored here
   for the same reason).
3. When ready to push: `gh repo create beckfordp/<name> --public
   --source=. --remote=origin --push`.
4. Inside the new directory, in Claude Code: run `/conductor:setup` and
   seed `conductor/tracks.md`'s `## Backlog` from `docs/user-stories.md` —
   same pattern as a service, once there's real feature work to track
   beyond the initial scaffold.
